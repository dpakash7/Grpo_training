==============================================================================
1. THE SHORT VERSION
==============================================================================

Question:  can a small model get better at maths from rewards for correct
           answers alone, with no worked solutions to copy?

Answer:    in this one run, yes. On 1,319 test problems, GRPO reached 47.5%
           strict accuracy against 34.8% for the untrained model (p = 5.5e-19).

The catch: one seed; the supervised comparison came out weak; 240 minutes of
           GRPO against 90 of SFT; and "reproduce in under 2 hours on a free
           GPU" has not been proven.

The biggest problems were silent. Runs exited with code 0 while training on the
wrong prompts or learning the wrong lesson. Most of the engineering effort went
into catching things that looked fine.

==============================================================================
3. KEY DESIGN DECISIONS AND WHY
==============================================================================

Separate repo outside OneDrive
  OneDrive would keep trying to upload the virtual environment and model files.
  It also keeps this project away from thamaq.

Rewards and parser first, on CPU
  The parser decides every score in the project. A bug there makes every later
  number wrong, and it costs nothing to test without a GPU.

Code judges the replies, not a model
  Correct = 1.0, format = 0.1, length = 0.05. Correctness dominates, so the
  model can't score well on format alone.

Test set only for final scoring
  Checkpoints are chosen on 200 validation problems held out of the training
  split. If you pick using test, the final number is no longer a fair estimate.

Time budget measured in training time
  Both trainers validate every 30 minutes of training. Validation time doesn't
  count against the budget, so slow evaluation can't eat into training.

Paired statistics
  All models answer the same problems, so McNemar compares them problem by
  problem. That is more sensitive than comparing two overall percentages.

Lenient accuracy, never used as a reward
  It takes the last number anywhere in the reply, which separates "bad maths"
  from "right answer in the wrong place". It's rough, and only for diagnosis.

Learning from the problem's own group (how GRPO works)
  Each reply is compared with the other 7 replies to the same problem, so the
  model gets no credit just because a problem was easy. No value network is
  needed, which saves memory.

4. WHAT WENT BAD
==============================================================================

4.1  Reward hacking in the first smoke run
  Saw:    replies collapsed to about 3 tokens within 20 steps [session].
  Cause:  no reply was ever correct, so the length penalty was the only signal
          left. TRL's default divides rewards by the spread within each group.
          A tiny spread made a 0.05-weight penalty act at full strength.
  Fix:    a usable prompt, plus scale_rewards: batch.
  Lesson: check what the model is really being paid for. A small weight doesn't
          guarantee a small effect.

4.2  The base model ignored the format
  Saw:    strict accuracy of 0 to 1% for every prompt, except the combination
          below, while lenient accuracy reached 56.5%. It could do some maths
          but wouldn't use the tags.

            Prompt                            Strict  Lenient  Format
            Instruction only                   0.5%    47.5%    0.0%
            Example in the system prompt       1.0%    51.5%    0.0%
            Example as a chat turn             0.0%    56.5%    0.0%
            Pre-filled <think> only            0.5%    13.0%    0.0%
            Example as chat turn + pre-fill   56.0%    59.5%   88.5%

  Fix:    used the last row for all three models.
  Cost:   I chose this on the same validation split later used to pick
          checkpoints. Disclosed in the README.

4.3  Stale dataset cache: the worst bug in the project
  Saw:    I changed the prompt, but GRPO kept training on the old one. Runs
          exited cleanly.
  Cause:  the datasets library reused a cached copy of the mapped data.
  Fix:    two commits. Caching is now off across the project, with a test.
  Lesson: exit code 0 only means nothing crashed. From smoke run 4 onward, I
          read the training metrics directly.

4.4  TRL closed the pre-filled reply
  Saw:    the prompt must end inside an open <think>, but TRL closed that turn
          for conversational prompts. No error.
  Fix:    GRPO now receives already-rendered strings, with a guard.

4.5  The GPU was too small for the settings
  Saw:    about 8 GB of memory wanted on a 6 GB card, at 75 s/step [session].
  Fix:    chunks of 4 replies instead of 8, still 32 replies per step through
          gradient accumulation. In the speed test: 3.06 GB and about 22 s/step
          [session]. Checkpointing stayed on, since the same test took 211 s
          with it on and 336 s with it off [session].
  Lesson: the real run later used about 5.9 GB [session] and was slower than the test.
          A 3-step test doesn't predict 4 hours.

4.6  SFT's selection kept nothing
  Saw:    all three trained validation scores were below the untrained start:

            SFT step    0: 56.0%   402: 50.5%   911: 44.5%   1,708: 49.0%

          Patience ended it after 3 failed checks, and selection kept step 0.
          So "SFT" on test is literally the base model.
  Fix:    scored checkpoint-1500 afterwards and labelled it post-hoc.
          Result: 35.6%, no detectable change from base (p = 0.60).
  Open:   checkpoint-1500 was the latest one saved, and wasn't one of the three
          validated steps. The final step 1,708 wasn't saved. One checkpoint
          can't rule out a better SFT.

4.7  Validation was far more optimistic than test
  Saw:    the same untrained model scored very differently:

            Validation (200 problems)            56.0%  (49.1-62.7)
            Other training problems (1,000)      47.1%  (44.0-50.2)
            Test (1,319 problems)                34.8%  (32.3-37.4)

  Checked: test answers line up with their problems, and rescoring matches, so
          it isn't a scoring bug.
  Reading: validation may be an easy draw. The train/test gap is too wide for
          chance. The model may have seen GSM8K's train problems before release,
          but that's untested.
  Risk:   if validation favours what the model already knows, it may have been
          biased against SFT during selection.

4.8  KL kept climbing, and replies got longer
  Saw:    KL 0.0019 to 0.1979, entropy 0.5535 to 0.0976 (mean of first 5 logs
          to mean of last 5). Test length 113.9 to 142.8 tokens. Clipped replies
          3.6% to 5.1%, and a clipped reply can't score.
  Reading: not a repeat of the collapse, since accuracy rose. But beta 0.001
          barely restrained the model, and the length penalty didn't stop growth.
  Trap:   sampled correctness rose from 0.2787 to 0.5694. Lower entropy pulls
          samples towards the greedy reply, so that overstates learning.

4.9  Smaller bugs
  - Parser accepted non-ASCII digits and "18..". Caught by tests, fixed.
  - Error bars crashed at 100% accuracy (negative yerr). Caught by a plot test.
  - New repo had no git identity. See 5.4.
  - PowerShell 5.1 mangled quotes in python -c, so I switched to script files.
  - Keep-awake flag as a hex string was risky in PowerShell 5.1. Passed as a
    plain number before launch. No power settings were changed.
  - Typo in compare_prompts.py, variants("")(). Fixed before running it.
  - A harmless "remove env var" error landed in that script's log. The saved
    environment file confirms it ran on the GPU.

4.10 Uneven speed, cause never found
  Saw:    25 to 78 steps per 30-minute window; logged step times from 18.1 to
          171.3 s.
  Suspects: GPU memory near its limit, other laptop use, and my own tests running
          alongside it early on. None confirmed. It's in the README as unknown.

  - 66% as a real score. It's the best of 9 noisy checks on 200 problems.


==============================================================================
7. WHAT I'D DO DIFFERENTLY
==============================================================================

  1. Tune SFT's learning rate before the comparison. This is the weakest part.
  2. Run at least 3 seeds. The single-seed effect is large, but its spread is
     unknown.
  3. Use a larger validation set. 200 problems gives about +/-7 points.
  4. Choose the prompt on a separate split from checkpoint selection.
  5. Keep failed-run logs from the first minute.
  6. Run smoke tests on validation only, never test.
  7. Always save the final checkpoint.
  8. Measure speed over 30+ steps with full validation before quoting an estimate.

9. GLOSSARY
==============================================================================

  GRPO           RL method: sample several replies per problem, reward each, and
                 push up the ones that beat their group's average.
  SFT            Supervised fine-tuning: learn by copying known good answers.
  LoRA           Train two small matrices added to a frozen weight matrix, instead
                 of retraining it. This is why it fits on a small GPU.
  KL             How far the model's choices have moved from the base model's.
  Entropy        How spread out the model's choices are. Low = more deterministic.
  Greedy         Always pick the most likely next token. Used for scoring.
  Sampling       Pick tokens at random by probability. Used in GRPO training.
  Reward hacking The model earns reward in a way you didn't intend.
  Wilson         A way to compute a 95% interval for a percentage.
  McNemar        A paired test that looks only at problems where two models differ.
  Post-hoc       Done after seeing results, so it's weaker evidence.
  Gradient       Add up gradients over small chunks before updating, so a big step
  accumulation   fits in small memory.
